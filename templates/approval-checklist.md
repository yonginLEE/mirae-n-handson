# 승인 체크리스트 v1

버전: v1 · 2회차

오늘 바뀐 점:
1. 모든 항목을 "예/아니오"로 답하는 문장으로 바꿨다("충분한가", "적절한가" 같은 표현 삭제).
2. 치명 이슈에 자격 증명(비밀번호·계정) 리터럴을 명시했고, 오류 경로 테스트와 요청 외 기존 파일 수정 항목을 추가했다.
3. 컨벤션 항목을 `CLAUDE_off.md:56-70` 의 modern/api 규칙에 맞춰 채웠다.
4. 시큐어코딩 체크리스트의 reviewer 담당 항목을 반영했다: 2-4(로그 개인정보), 2-5(객체 단위 권한), 4-10(서버 입력 검증, 경고 성격).

AI 가 만든 변경분 · 외주사 PR 을 머지하기 전에 리뷰어가 대조하는 목록이다. 네 기준이 **모두** 충족되어야 승인이다. 하나라도 미충족이면 반려. 각 항목은 **"예"일 때 충족**이고, 판정할 수 없으면 "확인 필요"로 따로 둔다. 미충족 기준은 아래 번호(예: 1-4, 2-1)로 적는다.

## 심각도 정의

- **치명** — 그대로 머지하면 서비스나 데이터에 피해를 줄 수 있는 문제. 1건이라도 있으면 반려.
  예: 채점 서버 계정 · 비밀번호가 `private final String` 리터럴로 들어 있다(pr-2, `GradingServerClient.java:28-29`).
- **경고** — 지금 고치지 않아도 동작하지만 다음 변경에서 사고가 될 가능성이 있는 문제. 승인 여부는 리뷰어가 판단한다.
  예: JSON 본문을 문자열로 이어 붙인다(pr-2, `GradingServerClient.java:56`). 반복문 안에서 쿼리를 한 번씩 보낸다(pr-1, `UnitService.java:38-39`).
- **제안** — 더 나은 방법이 있다는 의견. 승인 · 반려에 영향을 주지 않는다. 목록으로만 남긴다.

이슈 한 건은 심각도 · `파일:줄번호` · 근거 · 수정 방향 네 항목으로 적는다. 근거 줄번호는 실제 파일에서 다시 확인하고, 줄번호를 댈 수 없는 지적은 "확인 필요"로 따로 둔다. 비밀값은 문서에 옮기지 않고 `파일:줄번호` 만 적는다.

## 1. 테스트 통과

- [ ] 1-1. 변경된 모듈의 테스트 명령(`modern/api` 는 `./gradlew cleanTest test`)을 실제로 실행했는가?
- [ ] 1-2. 실행 결과에 실패 · 오류가 0건인가?
- [ ] 1-3. 기존 테스트를 지우거나 건너뛰게(`skip`, `@Disabled`) 바꾼 곳이 0건인가?
- [ ] 1-4. 새로 추가 · 변경한 public 메서드와 엔드포인트마다, 그것을 실행하는 테스트가 1건 이상 있는가?
- [ ] 1-5. 예외를 던지거나 오류 상태를 돌려주는 분기(404, 200 외 응답, `IOException` 등)마다 테스트가 1건 이상 있는가?
- [ ] 1-6. 앱에서 호출할 수 있는 새 엔드포인트마다 앱을 띄워 직접 호출했는가? (호출할 수 있는 새 엔드포인트가 없으면 "예")
- [ ] 1-7. 직접 호출하지 못한 엔드포인트가 있다면, 판정 문서에 호출하지 못한 사유를 적었는가? (호출하지 못한 것이 없으면 "예")

## 2. 치명 이슈 0건

- [ ] 2-1. 비밀번호 · 토큰 · 키 · 계정 ID 가 코드 · 설정 · 테스트 픽스처에 문자열 리터럴로 없는가? (`${x:값}` 형태의 기본값도 포함)
- [ ] 2-2. SQL 을 문자열로 이어 붙여 만드는 곳이 0건인가? (파라미터 바인딩 사용)
- [ ] 2-3. 데이터를 지우거나 덮어쓰는 코드가 새로 생겼다면, 요청 문장에 그 내용이 있는가?
- [ ] 2-4. 로그 · 응답 · 프롬프트에 학생 식별자 · 이메일 · 토큰을 원문으로 남기는 곳이 0건인가? (`templates/secure-coding-checklist.md` 10번)
- [ ] 2-5. 새 엔드포인트마다 요청한 사람의 데이터인지 서버에서 객체 단위로 검사하는가? (화면에서 숨기는 것만으로는 "아니오", 새 엔드포인트가 없으면 "예") (`templates/secure-coding-checklist.md` 19번)

## 3. 요청 범위 이탈 없음

- [ ] 3-1. 요청 문장이 한 문장으로 확인되었는가? (없으면 판정하지 않고 먼저 묻는다)
- [ ] 3-2. 변경 파일마다 요청 문장으로 설명되는가? (설명되지 않는 파일이 0개인가?)
- [ ] 3-3. 요청에 없는 기존 파일 수정(리팩터링 · "주변 코드 정리" 포함)이 0건인가? (있으면 별도 PR 로 분리해 달라고 요청한다)
- [ ] 3-4. 의존성 추가 · DB 스키마 변경 · 설정 파일 변경이 있다면, 요청 문장에 포함돼 있는가?

## 4. 컨벤션 준수

기준: `CLAUDE_off.md:56-70` 의 "modern/api (팀 컨벤션의 기준)". 팀 `CLAUDE.md` 로 옮겨지면 그 위치를 따른다. 출처를 찾지 못한 규칙은 위반으로 판정하지 않고 "확인 필요"로 둔다.

- [ ] 4-1. 컨트롤러가 서비스만 호출하는가? (Repository · SQL 직접 호출 0건)
- [ ] 4-2. `try/catch` 로 예외를 삼키고 아무 처리 없이 넘기는 곳이 0건인가?
- [ ] 4-3. 새 서비스 클래스에 `@Transactional(readOnly = true)` 가 있는가?
- [ ] 4-4. 응답 DTO 가 `record` 인가?
- [ ] 4-5. 현재 시각을 `Clock` 주입으로 얻는가? (`LocalDateTime.now()` 직접 호출 0건)
- [ ] 4-6. 문항 상태를 `ItemStatus` 상수로 쓰는가? (`"A"` 같은 문자열 리터럴 0건)
- [ ] 4-7. `System.out.println` · `console.log` 같은 임시 출력이 0건인가?
- [ ] 4-8. 테스트 이름이 `@DisplayName("메서드: 기대 동작")` 형식의 한국어인가?
- [ ] 4-9. 추가한 저장소 테스트가 모두 `@DataJpaTest` + `@ActiveProfiles("test")` 로 작성돼 있는가? (추가한 저장소 테스트가 없으면 "예")
- [ ] 4-10. 새 입력(파라미터 · 본문)을 서버에서 타입 · 범위 · 길이 · 허용 목록으로 검증하는가? (출처: `templates/secure-coding-checklist.md` 11번. 위 기준 문서 밖의 규칙이라 검증 코드가 없어도 승인을 막지 않고 경고로 남긴다)

## 판정 형식

첫 줄에 `판정: 승인` 또는 `판정: 반려`. 이어서 네 기준의 충족 · 미충족 표(미충족은 위 번호로 적는다), 그다음 이슈 목록(심각도 · `파일:줄번호` · 근거 · 수정 방향). 코드는 수정하지 않는다.
